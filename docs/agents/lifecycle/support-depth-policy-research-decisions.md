## 4. Concrete obligation templates

Recommend stable obligation IDs with revisioned definitions. Families select templates; they are neither support levels nor certifications. ## 5. Evidence adequacy, receipts and permitted reuse

### Separate three evidence classes

**Discovery** binds help/raw snapshot/source identity and mode grammar. **Controlled-binary mechanics** exercises production request, process, parser and adapter paths under deterministic scenarios. **Upstream provenance** binds actual output/effects to a version/target/build or an explicit compatible source contract. None substitutes for the others. A fixture authored to match the parser can test mechanics but cannot independently prove that upstream emits it.

**Adequacy review:** for each obligation, establish the production entry/symbol, setup, controlled stimulus, observed assertion and plausible counterexample the test excludes through existing tests and review/closeout records wherever sufficient; a separate per-obligation mapping record is not required. Review that removing the relevant production validation/parser/cleanup would fail the assertion; use bounded mutation/negative tests where practical. A reviewer binds the exact requirement/assertion mapping and content digests, not merely a test filename, count, coverage percentage or `typed=true`. Use the existing independent review/closeout authority; no permanent new reviewer role. Executor submissions cannot approve their own weakened requirements.

### Recommended receipt contents and rejection rules

Extend existing tests, runners, CI results, fixtures and validation/review/closeout artifacts to establish, directly or by reference, operation/promise and obligation IDs; P/O bindings from section 6; exact target/version; upstream binary and source/fixture provenance; production/test/dependency content hashes; toolchain, dependency resolution, features and relevant environment description; executable/argv/working-directory policy; requested and **actually executed** test inventories; per-case outcomes; start/end/result and bounded log hashes; producer/version and local-run or CI-run identity. Store no secrets or whole ambient environment. Expected result text alone is not producer provenance. A new xtask runner, receipt format, evidence file, sidecar or mapping record is a provisional implementation only if a concrete verification gap requires it under section 6; avoid parallel evidence pipelines, redundant captures and recurring review of unchanged admissible mappings.

Reject verification when tests are missing, filtered to zero, skipped/ignored rather than executed, aborted, or selected differently from the binding. Reject malformed/unknown receipt schemas, duplicate IDs, unresolved paths, unsupported producers, wrong agent/target/version, changed binaries/features/toolchain/build graph, stale assertions/fixtures/requirements, mismatched P/O without an explicit validated reuse binding, unexplained transformed fixtures, and a receipt copied from an unrelated CI job. A successful Cargo exit with zero tests is rejection, not `verified`.

Local receipts are reproducible repository evidence within the existing trust boundary, not remote attestation. Imported CI evidence must identify repository/workflow/run/attempt and actual checked-out/built tree, not only PR head association. Preserve K8's distinction: its conclusion resolver neither proves the build tree nor establishes the input-bound execution evidence required here. Contradictory qualifying runs require investigation; do not select a favorable run silently. Review and execution evidence must both remain valid at final acceptance.

**Default reuse:** exact target and upstream version only. Permit a maintainer-approved compatibility rule per obligation, with explicit versions/targets, invariant source/protocol/build assumptions, required residual target tests and invalidators. Pure parser mechanics may be reused under such a rule; process termination, ABI, path, permission and platform-required runtime proof cannot be waived by a cross-platform label. Output provenance for one version cannot become exact-version proof for another merely because help is unchanged. When a current O or generation differs, preserve the prior admissible depth receipt's original P/O and require a current E reuse binding for each reused obligation. Validate unchanged effective requirements, applicable trust/review rules and dependencies, plus exact version/target or the approved compatibility rule; run all newly due or changed cases. A bare mismatched receipt is invalid, and a pre-adoption successful closeout is not automatically an admissible depth receipt. Store this proof reference in existing evidence machinery, not a legacy-comparison ledger.

Relevant implementation/test/fixture/protocol/dependency changes invalidate affected receipts and adequacy bindings. Unrelated documentation churn does not. Reusing unchanged adequacy review does not reuse an execution result whose tested inputs changed. There is no legacy-unassessed carry mechanism. Evidence reuse is a positive, content-bound proof decision under the exact enrolled contract, never an exemption from satisfying it. Start with exact version/target reuse; cross-version/target compatibility rules are optional later work unless needed for the selected claim.

Reuse existing packet/report/closeout fields and references while preserving authority, scope and invalidation distinctions. Every proposed new field, artifact, registry, schema, approval step or persistent mechanism must identify the concrete reachable failure it prevents, why existing machinery cannot prevent it, and the smallest sufficient addition. Apply this necessity criterion within existing decisions and implementation review, not through a new justification document, checklist or approval gate. ## 7. Classification and shared-work ownership

Recommend exact selectors over canonical command path, interface owner/promise, explicit flag presence/value predicates and relevant defaults/config. Resolve aliases before matching; preserve discovery edges. Overlapping selectors with different effects or requirements are an error, not first-match precedence. A query's refresh flag, a debug command's output path, or a listener URL must not inherit harmlessness from the parent name. Unknown family/effect becomes `classification_required`. Proven ordinary additions within governed scope inherit the template without a new policy decision; changed risk or a relaxed obligation does not.

Associate discovered controls/defaults with the governed operation before resolving its accepted subset. A new flag/mode that does not match the former accepted value predicate cannot simply disappear into the unenrolled remainder. Determine its effect on the existing promise, required accounting and any proposed new scope. Outside depth selection, the existing maintenance/request/charter duties still decide whether wrapper work is required. Selection is additive to those duties, not the source of all support obligations.

An override should carry exact operation/mode, replacement obligation set, version/target bounds, rationale/evidence, maintainer approval reference and expiry/review condition. It cannot erase an existing promise or evade approved debt policy. Request generation displays the effective override and its authority; executors cannot author it during remediation. Once due, work remains due until satisfied or validly dispositioned, regardless of task location, current advertising, paused future enrollment or deleted declarations. Ending selection for a future generation cannot silently weaken an ongoing approved promise.

### Preserve the settled maintenance/additive split

Maintenance owns required wrapper work and preservation/repair of **existing** shared promises. Optional additions neither block required-wrapper completion nor count as debt or verified support. An unknown required wrapper behavior cannot be relabeled optional. Removing capability advertising does not discharge a frozen existing mapping; it is potentially a regression or a new scope decision. Onboarding's minimum integration and chosen profile remain required, not postponed into optional additive work.

Recommend the following logical interface now, with implementation deferred to packet P5. Reuse existing reports, approvals and packet state; the stages do not mandate separate files, schemas or approval steps. New packaging must meet section 6's necessity criterion:

| Stage / owner | Input and output contract recommendation |
| --- | --- |
| Discover — shared evaluator, exposed by separate cross-agent xtask entrypoint | Read eligible **landed** wrapper operations and approved promises, including older unmapped ones. Produce a derived candidate report; names/help alone are insufficient eligibility. Do not create a second coverage or qualification engine. |
| Group — evaluator proposes, maintainer adjudicates uncertain equivalence | Group by proved request/effect/output/error/lifecycle semantics, not equal command names. Retain stable operation IDs and acquisition edges; an uncertain equivalence is a visible candidate question, not an invented universal capability. |
| Select — maintainer or existing explicitly bounded approval authority | Bind selected operation IDs, participating agent versions/targets, wrapper promises/receipts, shared contract/capability inputs, exclusions and selected result. Discovery can be single-agent; selection is not approval to bypass minimum integration or publication rules. |
| Prepare — existing packet machinery | Reuse stable candidate IDs and compatible open packet IDs; freeze the selected input digest and exact write/evidence envelope. No duplicate packet because a newer discovery run found the same operation. |
| Execute/accept — bounded executor, independent checker/reviewer | Prove adapters through their actual production paths; reject stale participating-agent or shared-contract inputs at preparation, execution and acceptance. An unrelated nonparticipating-agent edit alone is not staleness. |
| Publish — existing publication consumers | Require approved advertising, adapter proof and the two-backend rule for non-allowlisted universal additions. A backend-namespaced result can remain backend-specific, but is not a promoted universal capability. |

Candidate lineage is a future contract test: if a group splits, each selected operation has one active disposition/packet owner; if groups merge, supersession and packet reuse prevent double work or lost obligations. Preserve links for unselected members, cancelled packets and obsolete candidates. Split/merge must not orphan a required existing mapping, duplicate a debt identity, or make an approved selection silently broader. Candidate reports are derived; approvals and open-packet state stay with their existing owners rather than becoming another mutable governance ledger.

## 8. Clean adoption, maintenance pilot and onboarding rehearsal

### Enrollment is prospective obligation, not a renamed exemption

Use existing approved packet/request/agent scope and authoritative policy linkage wherever sufficient, with deterministic resolution. Existing approval may authorize the relevant selection when its recorded authority suffices; no separate enrollment subsystem, duplicated registry, per-generation manual ceremony or status ledger is required. Scope omission or deletion still cannot waive independently due work.
